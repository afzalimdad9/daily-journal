# El código abierto es una licencia, no solo un precio

«Software gratuito» puede referirse a software que no cuesta dinero, a software que concede libertades importantes a sus usuarios o a ambas cosas. El software de código abierto tiene un significado más concreto: su licencia permite acceder al código fuente y concede permisos que cumplen la [Definición de Código Abierto](https://opensource.org/osd/). El precio por sí solo no indica qué puedes hacer con el código.

La diferencia importa tanto si eliges una biblioteca para un proyecto como si copias un pequeño ejemplo de código o publicas una herramienta propia. Los derechos de autor siguen vigentes. Una licencia es el permiso escrito del autor para usar, modificar y compartir la obra bajo unas condiciones determinadas.

## Lee la licencia del proyecto

Busca un archivo `LICENSE` o `COPYING` en el repositorio. Comprueba si el proyecto establece condiciones diferentes para determinadas carpetas, recursos o dependencias. Si el repositorio no tiene una licencia clara, no des por hecho que puedes reutilizar su contenido: pregunta al autor o elige código con condiciones que entiendas.

Comprueba también la versión que vas a utilizar. Un proyecto puede cambiar de licencia con el tiempo, y una dependencia puede incluir avisos independientes. La licencia de tu aplicación no sustituye automáticamente las licencias de sus componentes.

## Familias de licencias habituales, a grandes rasgos

Las licencias permisivas, como MIT y BSD, suelen permitir una reutilización amplia, incluso en proyectos propietarios, aunque exigen conservar los avisos y las exenciones de responsabilidad. La Apache License 2.0 permite una reutilización similar e incluye condiciones y términos expresos sobre licencias de patentes.

Las licencias copyleft, como la GNU General Public License (GPL), permiten usar, modificar y redistribuir el software, pero exigen que ciertas obras derivadas distribuidas mantengan la misma licencia y que el código fuente correspondiente esté disponible conforme a sus términos. Las obligaciones concretas dependen del texto de la licencia y del uso que se haga del software.

Estas son descripciones generales, no una lista para garantizar el cumplimiento. Por ejemplo, la GNU Lesser General Public License (LGPL) tiene condiciones distintas de la GPL, y la Affero GPL trata de otra manera el uso a través de redes. Cuando la diferencia sea importante, lee la licencia y busca asesoramiento cualificado para tu caso.

## Lleva un registro mientras desarrollas

Para un proyecto personal, empieza con un inventario sencillo de dependencias. Anota el nombre, la versión, el origen y la licencia de cada componente. Al redistribuir código, conserva los avisos de copyright y licencia que sean obligatorios. Si tu proyecto tiene un proceso de publicación, incluye la revisión de cambios de licencia al actualizar dependencias.

En un equipo o producto comercial, utiliza un proceso de revisión coherente en lugar de depender de la memoria de cada desarrollador. Una lista de materiales de software puede ayudar a identificar componentes, pero por sí sola no determina si todos los usos cumplen con cada licencia.

## Elige teniendo en cuenta las condiciones reales

Antes de adoptar una dependencia, pregúntate qué necesitas hacer con ella: usarla internamente, distribuirla a clientes, modificarla u ofrecerla como servicio alojado. Después compara esos planes con la licencia y los avisos del proyecto. La [guía para elegir una licencia](https://choosealicense.com/) ofrece una comparación accesible, y la [lista de licencias de Open Source Initiative](https://opensource.org/licenses) enlaza las licencias y sus textos.

El código abierto es un modelo de colaboración respaldado por permisos legales. Entender esos permisos ayuda a reutilizar software con respeto y a ofrecer la misma claridad a quienes utilicen tu trabajo.
